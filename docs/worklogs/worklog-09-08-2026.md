# Linux Provider Adapter Foundation

## Why

The planner and schema-v3 contracts already modeled Ubuntu, Fedora, and their package managers, but no Linux executor existed. A small, contract-driven adapter is the safest first step before adding dozens of reviewed provider mappings, privilege orchestration, a Unix bootstrap, or real installation flows.

## How

Added `internal/adapter/linux` with an injected process runner, per-distribution manager allowlists, native inventory commands, manager-specific typed installation argument builders, dry-run support, and direct process execution through `os/exec` without a shell. APT detection uses `dpkg-query` and requires the exact `install ok installed` status; DNF uses `list --installed`; Snap uses `list`; Flatpak uses scope-specific `info`. The implementation validates machine/elevated metadata for APT, DNF, Snap, and system Flatpak, user/user metadata for per-user Flatpak, and an explicit Flatpak remote.

The earlier roadmap identified platform order but did not give contributors enough sequencing, acceptance criteria, or runtime-boundary guidance to implement Linux safely. The new roadmap makes the immediate Ubuntu work concrete while preventing premature claims that the source-only adapter is already a runnable Linux setup.

## How

Reconciled the roadmap with the live v6.2.0 release, the v6.3.0-dev branch identity, schema-v2 production authority, the completed Linux adapter, current compiler limitations, the Windows-only broker, and the documented release/security constraints. Split Linux delivery into six ordered phases and added separate Windows cutover gates so Linux progress cannot silently change the released Windows runtime.

## Problems Encountered

The existing roadmap mixed completed architecture work, near-term platform priorities, and long-term cross-platform ideas without separating runnable behavior from source-only foundations. It also listed Ubuntu and Fedora as single milestones despite catalog, compiler, orchestration, bootstrap, and real-install validation being distinct risk boundaries.

## Solutions

Reorganized the roadmap around verifiable delivery phases and acceptance gates. Kept provider catalog generation deterministic, prohibited profile forks and mutable bootstrap execution, separated user and machine privilege work, and required explicit unsupported intent instead of silent package omission.

## Bugs Found

No code bug was found. The roadmap had a planning-quality defect: it was too terse to prevent ambiguous implementation order or premature Linux readiness claims.

## Bug Fixes

Replaced the ambiguous platform bullets with scoped checklists, runtime boundaries, release gates, and definitions of done tied to existing architecture and security decisions.
